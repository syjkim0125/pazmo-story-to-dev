# pazmo-story-to-dev

사람은 **무엇을 왜 만드는지**를 정하고, 다 만들어진 결과를 **한 번** 확인해요. 그 사이의 세부 결정, 작업 나누기, 개발, QA, 보안 점검은 AI가 해요.

```
/story <요청>
  1 크기 판단 → 계획 작성 → ★ 사람 승인 (작은 작업은 기다리지 않아요)
  2 개발 (세부는 AI가 정하고, 정한 것을 적어 둬요)
  3 QA 실행(qa-runner) + 보안 점검 + 코드 리뷰, 동시에
  4 고치고 다시 확인
  5 최종 리뷰 → ★ 사람 판단 → (켰을 때만) dev 머지
```

사람이 끼어드는 곳은 ★ 두 곳뿐이에요.

> 0.4.0에서 `/story` 하나가 한 줄 수정부터 Epic까지 받아요. 승인은 계획에 한 번이에요. 0.3.0에 따로 있던 QA Story 승인은 없어졌어요. QA 시나리오는 사람이 승인한 예시에서만 나오고, 승인 뒤에 요약을 알려 줘요. 계획 양식도 바뀌어서 MUST 대신 "사용자가 보게 될 것" 예시를 써요.
>
> 0.3.0에서 `/story-qa`가 `/story`와 `/qa`로 바뀌었어요.

## 크기는 AI가 판단해요

명령은 하나예요. AI가 코드를 읽은 뒤, 고치기 전에 작업 크기를 정하고 한 줄로 알려 줘요. 사람은 한마디로 바꿀 수 있어요.

| | 작은 작업 | 중간 작업 | 큰 작업 (Epic) |
|---|---|---|---|
| 기준 | 해석이 하나, 모듈 하나, 위험 결정 없음, 예시 두 개 이하 | 작지도 크지도 않은 것 | 예시가 다섯 개를 넘거나, 사용자 흐름이 둘 이상이거나, 새 하위 시스템 |
| 시작 | 이해한 내용 한 줄, 기다리지 않음 | 계획 초안 한 번에 보여 주고 승인 한 번 | 대화로 계획을 다듬고 승인 한 번 |
| 개발 | 메인 세션 | 메인 세션 | 태스크마다 새 빌더 에이전트 |
| 코드 리뷰 | 없음 | 한 번 | 끝에 한 번 |
| QA | 사용자가 보는 변화가 있을 때만 | 예시 전부 | 예시가 완성될 때마다, 끝에 전부 |
| 보안 | 스캐너 | 스캐너 + `security-review` | 같음 |
| 끝 | 짧은 보고 | 최종 리뷰 | 최종 리뷰 (약 30분) |

- 헷갈리면 한 단계 위로 잡아요.
- 돈·인증·이관·외부 연동·저장 데이터에 닿으면 최소 중간이에요.
- 작업 중에 범위가 커지면 AI가 크기를 올리고 알려 줘요. 내리지는 않아요.

## 계획에서 사람이 정하는 것

- **범위의 폭:** AI가 가장 작은 해석과, 더 넓게 읽으면 들어가는 항목을 나열해요. 사람이 항목별로 골라요. AI는 어느 쪽도 추천하지 않고, 답하지 않은 항목을 스스로 빼지 않아요.
- **사용자가 보게 될 것:** `어디서 · 무엇을 하면 → 무엇이 보인다` 꼴의 예시에 예/아니오로 답해요. 이 예시가 그대로 QA 시나리오가 돼요.
- **위험 결정:** 돈, 이관, 인증, 외부 계약, 저장 데이터에 관한 결정은 AI가 고르지 않아요 (`references/risks.md`).

그 밖의 것(언어, 라이브러리, 구조, 데이터 모델, 작업을 나누는 방법과 순서, 테스트 방식)은 AI가 묻지 않고 정해요. 사용자가 보는 것, 저장되는 것, 되돌리기 어려운 것을 바꾸는 결정은 `docs/stories/<slug>.decisions.md`에 "제안" 상태로 적어 두고 최종 리뷰에서 보여 줘요.

## 단계마다 하는 일

- **계획:** 왜, 사용자가 보게 될 것, 범위, 사람이 정할 것, 품질 기준. 큰 작업은 사용자, 출시 뒤 지표, 운영 방식이 더 들어가요.
- **QA Story:** `qa-writer` 에이전트가 계획과 앱 실행 방법만 보고 써요. 코드와 diff는 보지 않아요. 만든 걸 확인하는 QA가 아니라 요청한 걸 확인하는 QA가 되게 하려는 거예요. 계획이 승인된 뒤에 쓰고, 시나리오는 승인된 예시·그대로인 것·품질 기준에서만 나와요. 몇 개인지와 못 채운 빈칸을 한 줄로 알려 주고, 앱을 띄울 수 없는 빈칸일 때만 멈춰서 물어요.
- **개발:** 작은 작업과 중간 작업은 Claude가 원래 하던 대로 해요. 큰 작업은 AI가 태스크로 나눠 하나씩 새 빌더 에이전트에게 맡겨요. 빌더가 끝날 때마다 계획·QA Story·`qa/`를 건드렸는지 git으로 확인하고, 건드렸으면 되돌려요.
- **QA 실행:** `qa-runner` 에이전트가 시나리오를 `qa/<slug>.sh` 같은 스크립트로 만들고, 빈 포트로 앱을 띄워 돌리고, 앱을 꺼요. 앱이 안 뜨면 다른 방법으로 때우지 않고 "실행 안 함"으로 보고해요. 큰 작업에서는 이 결과만 태스크를 "통과"로 바꿔요. 빌더가 "다 했다"고 해도 통과가 아니에요.
- **멈추고 넘기기:** 계획에 답이 없는 위험 결정, 범위 변경, 되돌릴 수 없는 단계, 틀려 보이는 예시를 만나면 AI는 고르지 않아요. 거기에 걸린 일만 세워 두고 나머지를 만든 뒤 최종 리뷰에서 물어요.
- **고치기:** 실패한 시나리오나 확인된 취약점은 고치고, 고친 곳이 닿는 시나리오만 다시 돌려요. 두 번 해도 남으면 멈추고 보고해요.
- **최종 리뷰:** 아래 형식으로, 띄운 앱에서 확인해요.

수정 뒤에 QA만 다시 돌리거나 다른 환경(preview, dev)에서 돌리려면 `/qa <story 경로> [local|preview|dev]`를 써요. 승인된 QA Story가 있으면 다시 묻지 않고 저장된 스크립트를 돌려요.

## 최종 리뷰

diff를 읽는 대신 띄운 앱에서 직접 해 봐요.

1. **의도:** 계획의 "왜"와 "결과" 그대로, 예시별로 됨·일부·안 됨, 계획에 없는데 더한 것, 범위인데 뺀 것.
2. **해 보기:** 예시마다 "이걸 하면 이게 보여야 해요" 한 줄. 그다음 사용자라면 처음 할 일을 직접 해 봐요.
3. **결정:** AI가 정한 것 중 되돌리기 어려운 순으로 최대 7개. 근거 설명이 아니라 "틀렸다면 이렇게 보여요"와 어디서 확인하는지를 적어요.
4. **근거:** QA 표, 품질 검사 수치와 기준, 보안과 리뷰 결과.
5. **사람이 정할 것:** 개발 중 멈춰 둔 결정.
6. **확인하지 못한 것:** 안 돌린 검사와 이유, 사람만 할 수 있는 단계, 출시 뒤에만 알 수 있는 것.
7. **판단:** 수락 / 고쳐서 수락 / 방향이 다름.

## 품질 검사

중간 작업과 큰 작업의 계획에는 품질 기준이 들어가요. AI가 작업 종류에 맞는 기본값을 넣고, 사람은 승인할 때 바꾸기만 해요.

| 검사 | 언제 | 기준 | 누가 확인 |
|---|---|---|---|
| 접근성 규칙 검사 (axe-core) | 웹 화면이 있을 때 | WCAG 2.2 A·AA 위반 0 | 스크립트 |
| 키보드·포커스 | 웹 화면이 있을 때 | 모든 컨트롤에 Tab으로 닿고, 포커스가 보이고, Esc로 닫힘 | 에이전트 |
| 좁은 화면·큰 글자 | 웹 화면이 있을 때 | 320px 폭과 글자 200%에서 가로 스크롤과 잘림 없음 | 에이전트 |
| 빈·로딩·오류 상태 | 데이터 화면이 있을 때 | 세 상태가 모두 있고, 오류는 고치는 법을 알려 줌 | 에이전트 |
| 성능 (실험실 측정, Lighthouse) | 계획에 예산을 적었을 때만 | 5회 중앙값 LCP 2.5초 이하, CLS 0.1 이하 | 스크립트 |
| 코드 건강 | 중간·큰 작업 전부 | 이 브랜치가 바꾼 줄에 저장소 자체 린터 경고 없음 | 보안 에이전트 |
| 하드코딩된 문구 | 다국어일 때만 | 새 코드에 없음 | 보안 에이전트 |
| 스크린 리더 | 웹 화면이 있을 때 | 핵심 흐름을 끝까지 할 수 있음 | 사람 (최종 리뷰) |
| 실사용 성능, 번역 품질, 성공 지표 | | | 출시 뒤에만 |

- 규칙 검사 위반 0은 최저선이에요. 자동 규칙은 WCAG의 일부만 보고, 키보드·포커스 문제는 직접 걸어 봐야 보여요.
- 실험실 성능은 실사용 성능이 아니에요. 출시 전에는 실사용 수치를 "확인함"으로 적지 않아요.
- 못 돌린 검사는 "실행 안 함"과 이유를 적어요.
- 접근성 검사는 `@axe-core/cli@4.14.0`, 성능 측정은 `lighthouse@13.6.0`을 버전을 고정해 불러요. 둘 다 Node 22.19 이상과 Chrome이 필요해요. 접근성 검사의 `chromedriver`만은 설치된 Chrome의 주 버전을 따라가요. 드라이버가 Chrome과 맞지 않으면 검사가 시작되지 않기 때문이에요. 저장소에 자체 명령이 있으면 `docs/qa.md`의 `Quality checks`에 적어서 그걸 쓰게 할 수 있어요.

## 보안 점검

1. **[`@pazmo/cli`](https://www.npmjs.com/package/@pazmo/cli)** 스캐너: `PAZMO_NO_TELEMETRY=1 npx -y @pazmo/cli@0.1.3 scan . --json --base <기준 커밋>`
   - 모델 없이 돌아요: 오픈소스 SAST 규칙(Opengrep 엔진), 커밋된 비밀번호·키(Gitleaks), npm·Maven·Gradle 의존성의 알려진 취약점(OSV), 워크플로·AI 에이전트 설정, 저장소의 팀·회사 규칙(`.pazmo/`).
   - `--base`로 브랜치가 갈라진 커밋과 비교해서, 이 브랜치가 새로 만든 문제만 골라 줘요. 원래 있던 문제와 저장소 전체 문제(lockfile 없음 등)는 보고에서 빠져요.
   - 끝날 때 숫자 `0`·`1`은 검사가 돈 것이고, `2`는 명령 오류예요. 다 보지 못한 곳이 있으면(커밋 안 한 파일, `pom.xml`처럼 버전이 일부만 적힌 파일 등) "일부만 검사함"으로 보고하고 이유를 `확인하지 못한 것`에 적어요.
   - 엔진 버전이 고정돼 있고 sha256으로 검증한 뒤 실행해요. kit는 스캐너 버전을 고정해서 부르고, 다른 곳에서 알려 주는 설치 방법은 따르지 않아요.
   - kit가 부를 때는 텔레메트리를 꺼요(`PAZMO_NO_TELEMETRY=1`).
   - macOS(Apple 실리콘·Intel)와 Linux(x64·arm64)에서 돌아요. Node 20 이상이 필요하고, 기준 커밋이 저장소에 있어야 해요(얕은 clone이면 실행 안 함). 못 돌리면 "실행 안 함"과 이유를 보고하고 아래 2번은 그대로 돌아요.
   - 라이선스는 PolyForm Shield 1.0.0이에요. 쓰는 건 자유이고, 경쟁 제품을 만드는 데만 쓸 수 없어요.
2. Claude Code 내장 **`security-review`**: 권한 우회나 여러 파일에 걸친 인젝션처럼 코드 흐름을 따라가야 보이는 문제를 봐요. 작은 작업에서는 돌리지 않아요.

스캐너는 새 문제만, `security-review`는 이 브랜치의 변경만 봐요. 둘을 합친 뒤 코드를 따라가 확인된 것만 고치거나 사람에게 넘겨요.

**같이 쓰면 좋은 것:** Anthropic 공식 [`security-guidance`](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/security-guidance) 플러그인의 패턴 경고는 개발 중에 위험한 코드를 바로 알려 주고 토큰 비용이 없어요. 이 플러그인의 모델 리뷰(매 턴, 매 커밋)는 위 보안 점검과 겹쳐요.

## 설치

Claude Code:

```sh
claude plugin marketplace add syjkim0125/pazmo-story-to-dev
claude plugin install pazmo-story-to-dev@pazmo-story-to-dev
```

새 세션에서 `/story <요청>`으로 시작해요. 다른 플러그인과 이름이 겹치면 `/pazmo-story-to-dev:story <요청>`을 써요.

플러그인 에이전트가 없는 도구(Codex 등)에서는 `/story`가 크기와 상관없이 한 세션에서 개발까지 하고, 새 세션에서 `/qa <story 경로>`를 실행하라고 알려 줘요. 보안 점검과 코드 리뷰는 그 `/qa` 세션이 QA 뒤에 이어서 돌려요.

## 저장소마다 할 일

`docs/qa.md`를 [QA-ENV.md](skills/qa/assets/QA-ENV.md) 양식으로 둬요. 없으면 첫 실행 때 `qa-writer`가 README와 실행 스크립트로 초안을 만들고, 모르는 칸은 보고에 적고, 앱을 띄우거나 로그인하는 데 필요한 칸만 물어요.

- 운영 환경은 QA에 쓰지 않아요.
- `Target`은 기본 `local`이에요. PR마다 임시 환경이 뜨면 `preview`로 바꿀 수 있어요. 이때만 AI가 브랜치를 푸시하고, 최종 리뷰도 그 주소에서 해요. `local`이면 AI가 앱을 띄우고 주소를 알려 줘요.
- 여러 Story를 동시에 QA할 때 로컬 DB를 같이 쓰면 `Database: shared`로 적어요. 데이터를 바꾸는 시나리오는 하나씩 돌아요.
- `Auto-merge`는 기본 `off`예요. 사람이 `on`으로 바꿔야 AI가 dev 브랜치로 PR을 머지해요. 중간 작업과 큰 작업은 사람이 최종 리뷰를 수락한 뒤에만 머지해요. main에는 절대 머지하지 않아요.
- dev QA가 실패하면 AI는 고치지 않고 보고와 revert PR까지만 해요. 되돌릴지는 사람이 정해요.
- dev QA를 CI로 돌리려면 `qa-dev.yml`을 `.github/workflows/`에 복사하고 저장소 변수 `DEV_BASE_URL`, `DEV_VERSION_PATH`(배포된 커밋이 보이는 경로, 예: `/version`)를 정해요. 실패 원인 분석까지 원하면 `qa-dev-triage.yml`과 `ANTHROPIC_API_KEY` 시크릿을 더해요.

## 왜 이렇게 나눴나

예전 버전은 작업마다 개발 중에 QA 목록, QA 환경 문서, QA 스크립트를 준비했어요. 순정과 같은 작업으로 재 보니 결과물은 나아지지 않고 시간만 더 들었어요. 그래서 개발은 순정에 맡기고, QA는 개발이 끝난 뒤 따로 돌려요.

요즘 모델은 kit 없이도 코드를 잘 써요. 그래서 kit가 보태야 하는 건 코드 품질이 아니라 **방향**과 **제품 품질**이에요. 사람이 처음과 끝에만 있으니 세 가지에 무게를 뒀어요.

1. 시작할 때 요청의 해석, 특히 범위의 폭을 사람이 정해요. AI는 요청을 좁게 읽는 쪽으로 기울어요.
2. 중간에는 만든 쪽이 쓴 어떤 것도 "다 됐다"는 증거가 되지 않아요. 통과는 만든 쪽이 고칠 수 없는 검사가 정해요.
3. 끝에는 diff를 읽지 않고도 방향을 판단할 수 있게, 띄운 앱에서 직접 해 보게 해요.

근거와 한계는 [docs/research/2026-11-25-epic-planning.md](docs/research/2026-11-25-epic-planning.md)에, 설계는 [docs/superpowers/specs/2026-11-25-epic-design.md](docs/superpowers/specs/2026-11-25-epic-design.md)에 있어요. 큰 작업의 개발 절차(태스크마다 새 빌더)는 벤더 보고에만 근거가 있어서, 순정 세션과 비교해 이득이 없으면 빼기로 했어요.
